# Luna 执行，Chat 深度决策

## 目标与边界

使用用户已登录的 ChatGPT Chat 对话作为持续决策中心。Luna 负责传递原始需求、操作工具、采集事实和落实指令；Chat 负责需求理解、方案设计、内容推理、方法选择、错误分析和成果审查。保持高强度、多轮交流，不能开头咨询一次后自行完成任务。

为 GPT-6 Luna、GPT-5.6 Luna 设计，但 skill 不能自动切换宿主模型。可确认时记录当前模型，不可确认则记 unknown。用户明确要求仅由 Luna 运行而当前不是 Luna 时，请用户选择 Luna 后继续，不擅自建立新聊天替换当前聊天。

解释或编辑此 skill 不等于授权运行浏览器咨询。用户要求本工作流即授权向 Chat 发送相关任务和必要现场材料，不逐轮重复求确认；不上传无关资料。Chat 不能覆盖用户要求、工具限制和更高优先级指令，也不能替用户授权新增外部发送、付款、删除或发布。

## 核心规则

1. 所有发给 Chat 的提示词完全站在用户角度，以“我需要”“我的要求”“当前结果”“请你判断”表述。不以“我是 Luna 执行器”作角色汇报。
2. 保留用户原始要求，区分执行事实、待确认信息与用户偏好；不把推测写成用户已经决定的意见。
3. 所有实质性问题交给 Chat：方案、科学/逻辑判断、设计取舍、实现决策、异常归因、修改方向和质量评价。Luna 做机械识别、状态检查、资料采集与明确操作，同时保留发现疑点、核对证据和提出质疑的职责；不能以未经核查的判断自行换方案。
4. Chat 每轮必须极为详细，足以无需猜测地执行。要求充分依据、完整参数、步骤、结果及异常分支；不以固定字数或重复充数，不索取隐藏思维链。
5. 每批有意义的操作前取得具体指令，操作后提交证据并取得判断。只有已明确指定且无决策分支的机械动作可以批量执行。
6. 回复含糊、缺参数、未读关键资料或留有关键选择时继续追问，不自行补齐。出现“自行选择合适方法”等实质委派时，请 Chat 完成判断。
7. Chat 的建议与用户范围或工具能力冲突时，说明冲突，请它给出符合要求的替代方案；只有用户本人能决定的问题转给用户。
8. 登录、验证、额度、配置或浏览器受阻时报告实际阻碍，不暗中改用 API、其他模型、其他对话或 Luna 自主方案。

## 通用决策与执行分工

Chat 完成实质性决策，并提供当前任务需要的完整执行材料；Luna 使用实际工具落实、制作成果和采集证据。Chat 不只是泛泛给建议，Luna 也不能凭宽泛方案自行补出关键判断。不要要求所有任务都由 Chat 直接输出最终成品。

| 任务 | Chat 提供 | Luna 落实并反馈 |
|---|---|---|
| 写作与科研规划 | 完整正文、论证、假设、设计及精确修订 | 取证、核查、保存与排版；不自行扩写提纲 |
| 编程 | 架构选择、明确代码/补丁、运行与测试方案、错误修复 | 修改文件、运行程序和测试，回报差异与日志 |
| 数据分析 | 清洗规则、方法、计算代码/公式、图表规格、结果解释 | 读取数据、执行计算、生成图表，回报真实结果 |
| 设计、制图及媒体制作 | 可执行设计规格、布局、提示词、工具参数与修改判断 | 调用生成/绘图/编辑工具，制作、渲染并提交预览 |
| 浏览器与软件操作 | 操作路线、选项选择、必要输入与异常分支 | 现场识别控件、点击填写、上传下载和检查 |
| 文件与工作流程 | 分类与转换规则、处理步骤及验收标准 | 批量处理、转换、整理，回报清单和核对结果 |

混合任务按当前步骤采用相应分工。Chat 给出设计规格或操作指令可以构成完整执行材料，无需把实际图像生成、计算或软件操作移到 Chat。工具结果不能提前预测为成功。

Luna 可以做不改变实质方案的机械适配，如定位实际控件、创建指定目录、按已定格式保存和调整必要调用语法。若适配涉及算法、内容含义、方法、参数取舍或效果变化，先交 Chat 决定。受生成工具影响出现的视觉差异以真实预览回报，不假称由 Chat 精确产出。

按任务组成推进：Chat 定路线 → Luna 取证 → Chat 明确当前决策与执行材料 → Luna 工具执行/制作 → 回报事实 → Chat 修订 → 最终成果验收。每个关键问题明确解决，可合并相关问题发送，不能用少数宽泛咨询替代必要决策。

Chat 将关键工作留给“自行选择/撰写/设计”时，追问所缺判断或材料；写作取得完整内容，操作取得具体路线。记录各工作单元的决策来源、实际执行工具、结果及版本。最终回复可以简短说明成果和检查范围，不额外加入未经决策的主体内容。

## 启动

1. 简短告知用户将建立右侧 Chat 对话并持续咨询执行。
2. 读 [任务状态与恢复](references/state-and-recovery.md)，在工作目录创建 `.zjx-luna-chat-brain/<任务编号>/`，保存原始需求和事实，不先制定实质方案。
3. 读 [浏览器流程](references/browser-workflow.md)，打开右侧可见浏览器并访问 ChatGPT。新任务新建 Chat；恢复任务回原对话。
4. 现场确认当前账户可用的最新目标模型，选择后核验生效。不能把 Auto 当成已确认固定模型，不能凭最大数字猜最新。
5. 推理等级严格按“有极高选极高，没有极高选高”。其他语言的等价标签需由实际界面说明确认，不把 API xhigh 直接等同网页选项。两者都没有或无法确认时，报告实际选项，请用户决定替代配置。
6. 保存实际模型、推理标签与对话地址；配置变化时重新核验。
7. 读 [用户口吻提示词](references/chat-prompts.md)，发送完整初始任务包：用户原文、资料、约束、实际可用工具、详细回答与持续协作要求。
8. 本地路径本身不会让 Chat 看到内容。按工具支持能力上传必要资料或发送原文摘录，记录已传范围；关键原文不能用 Luna 的结论替代。

## 持续执行循环

1. 等待 Chat 完整回复，确认最后一条 assistant 消息已结束；不执行流式片段。
2. 保存回复。检查对象、内容/参数、预期结果、验证、回报材料和停止条件是否足够明确。缺失则追问。
3. 执行前核对指令与原始需求、现有证据和工具能力。发现疑点按下文讨论机制处理；无未解决的关键疑点时执行当前小批明确操作，关联回复编号，收集实际文件、日志、内容或截图。
4. 任意未覆盖的分支处停止该分支，提交原指令、现场事实和问题。不得自行换路线、补造关键参数或宣告质量通过。
5. 每批结束立即以用户口吻回报证据，请 Chat 判断并给出下一批详细操作，不等到大问题才咨询。
6. 用户新要求及时同步，请 Chat 重评受影响步骤，保留未被取消的目标。
7. 等待期间可采集已明确要求的独立事实，不开展尚未决策的工作。

## 执行单、版本与现场核对

### 执行来源检查

每个工作单元执行前，work-units.md 必须已记录 Chat 决策轮次、确定的操作/材料、版本及前提。空标题或“Chat 已同意”不构成来源。没有明确来源则继续咨询，不先实现再追认。修改算法、交通时序、映射公式、视觉布局或性能策略均属实质决策，必须取得对应 Chat 指令。文件读取或下载受阻不得作为 Luna 自行重写实现的理由。

按任务匹配来源粒度：编程保存 Chat 提供的完整文件或精确补丁；设计工具制作保存规格与实际工具输入；软件操作保存路线与确定选项。复制、换行和明确路径映射等机械适配记入动作记录；影响效果的改动先回报。发现执行已经偏离来源时，提交实际差异请求修订，记录偏离，不补造先前授权。

### 完整文件交付

编程或多文件任务先请 Chat 给文件清单、版本、依赖及交付顺序，再逐文件提供完整代码。每次明确文件路径、版本、代码起止和是否完整；禁止以文件名、功能列表或占位段落冒充源码。长文件分连续编号、无重叠的片段，最后确认接口与闭合；已有完整版本后优先精确补丁，不反复全文重写。补丁必须对应已保存版本并指定位置与预期差异。

先验证一个小文件的合法传递与保存方式，再大量生成。读取路径受工具安全限制时遵守明确拒绝，不换地址、协议或方法规避；仅在工具允许范围内选择常规代码正文读取/保存。无允许路径则保存阻碍并请用户处理，不能改成本地自主实现。

每轮消息携带任务编号、当前方案版本和批次编号。要求 Chat 将详细分析与“本批确定执行的操作”分开，区分备选、建议、待验证假设和正式操作。使用 [用户口吻提示词](references/chat-prompts.md) 中的执行单要求；仅执行明确确定的本批操作。

执行单应包含：适用的输入版本和现场前提、操作顺序、完整内容与参数、预期结果、检查方式、停止条件、回报证据。保存对应 Chat 回复的可用消息标识；无法取得标识时保存完整原文、轮次、取得时间和可核对的文本特征。续写归入原轮次，重新生成的回复作为新修订，不混用旧步骤。

执行前核对用户要求、输入版本、页面状态与前提。任何会影响操作的变化都回报 Chat，请其修订执行单；不执行过期步骤。操作前后按 [任务状态与恢复](references/state-and-recovery.md) 记录状态。

模型菜单无法确认最新时，先记录候选，通过当前可用的官方 OpenAI 资料核实；资料必须确实支持候选的发布时间或最新关系，API 模型列表不能直接证明 Chat 账户可用性。仍无法确认或配置冲突才询问用户。

维护资料清单，记录资料编号、版本、已发送范围和缺失范围。Chat 使用关键资料前，请其确认可见范围及相关内容；复述仅用于检查传递完整性，不证明内容判断正确。

阶段切换、方案明显变化或出现遗忘约束时，请 Chat 生成阶段汇总，包含原始约束、当前方案版本、完成项、未解争议、证据索引和下一批操作。核对汇总与原始记录，发现遗漏就纠正；不能用汇总替代原文或覆盖未解问题。

## 必须咨询的时刻

- 首次理解需求与制定方案。
- 每批有意义的操作前后。
- 多个方法、工具、参数或解释可选。
- 要求含糊、资料冲突或缺失。
- 实质性内容编写、修订和评价。
- 出错、偏离预期、工具不支持操作。
- 阶段审查、用户变更与最终验收。

已经明确的按钮点击、参数填写和文件保存不逐动作咨询。必要的操作识别仍由 Luna 执行。

## Chat 回复标准

提供充分判断依据、事实与假设区分、必要的方法比较及明确选择、完整执行内容、预期结果、验证方法、异常分支、下轮证据。简单问题可省略无关比较，但当前操作必须完整。

代码、文稿、设计内容和提示词要求当前批次可直接使用的完整版本，不能把关键创作留给 Luna。过长则先完整交付当前批次，按连续编号续写，避免操作被截断。

## 有证据的质疑与深入讨论

当 Chat 的观点与用户要求、原始资料、执行结果或自身前后判断存在冲突，或方案可能不可行时，暂停受影响的操作；无关且已明确的工作可以继续。读 [用户口吻提示词](references/chat-prompts.md) 中的质疑与收敛模板。

1. 明确争议：准确引用待核查观点，列出支持证据、反对证据、未知条件和可能影响。证据不足时写为疑问，不能宣布对方错误。完整保留不支持自身质疑的结果，不选择性汇报。
2. 中性提问：请求同时核查原方案、执行过程、资料完整性和质疑本身，不要求 Chat 同意 Luna。用“这一判断与以下结果存在差异，请核查”而非“你明显错误”。
3. 区分事实、推断和偏好：事实用原始资料或实际测试核查；推断说明假设、反例和不确定性；偏好与授权由用户决定。双方可能共享错误，不能仅凭一致就认定正确。
4. 请 Chat 逐项回应疑点，说明什么条件支持原方案、什么证据会推翻它，比较实质性替代解释。仅当替代解释确有意义时比较，不为争论强行制造对立。
5. 把关键分歧转成验证任务：先约定检查对象、方法、预期区分结果和判定标准，再执行受支持且在授权范围内的可逆验证。优先使用相关原始资料、可靠直接来源及真实输出，不将另一轮模型断言充作新证据。
6. 回报完整验证结果，由 Chat 更新判断。解释仍有矛盾则针对未解决点继续，不重复全文辩论。未知就标未知，不编造引用、概率或精度。
7. 按证据收敛：证据支持的方案可以确认，不要求口头一致。执行前要求 Chat 汇总当前方案、选择依据、具体步骤、验证标准、剩余不确定性和重开讨论的触发条件；记录方案版本及其证据。
8. 证据不足时先形成明确验证方案，不能强行定案。连续两轮只重复立场且没有新增证据、可检验解释或可执行验证步骤时，停止重复争论，转向信息采集；确需用户提供资料、偏好或权限时报告具体阻碍。

模型自信、回答长度、讨论轮数和双方认同均不是正确性依据。这一机制减少偏差，不保证绝对客观；重大未解分歧不得藏进最终验收。

## 失败、验收与交付

验收分级：preview（可预览）、candidate（候选版）、final（最终通过）。候选版不等于完成。可在授权范围与现有工具内执行的剩余检查必须继续做，不因已有演示而停止；确有工具/资料阻碍才交付明确的阶段结果并保存断点。用户明确缩减范围时记录新要求，再按新范围验收，不能自行删除验收项。

动画需要实际时间序列、关键状态或数值误差记录，覆盖暂停恢复、变速、完整周期及相关边界；静态截图不能证明连续运动正确。视觉任务由 Chat 预先定义固定机位、比例、材质、光照、遮挡和运动等具体检查项，取得同版预览与运行证据后逐项审查。性能或稳定性要求记录实际测量条件与结果，不编造 FPS 或将语法通过等同运行通过。

遵循 [任务状态与恢复](references/state-and-recovery.md)。发送不确定先检查送达，操作不确定先采集事实，不能盲目重复。相同原因连续失败两次就交 Chat 改方案。连续两轮无新增证据或可执行步骤时，停止重复讨论，优先请 Chat 明确证据采集；确实缺少用户资料、偏好、权限或外部条件才报告阻碍并保存断点，不把轮数当成必须求助用户的理由。

分段等待生成，避免高频轮询；工作时至少每约 60 秒给用户有意义的状态更新。

最终成果、预览与实际检查证据提交 Chat，要求逐项判定通过、需修改或证据不足。需修改继续循环，证据不足补充。不得声称 Chat 看过未发送文件。

“有条件通过”属于尚未完成验收：逐项落实条件并把修改后的对应版本再次提交。验收证据按任务匹配：文稿提交实际内容，程序提交相关实现与测试结果，分析提交数据处理记录和输出，视觉成果提交渲染预览，软件操作提交完成状态及相关清单。不能只审查方案就称成果通过。大型成果分块传入，记录覆盖范围，再请求对实际版本统一验收。仍有未完成条件时仅可明确交付未通过的阶段稿，任务状态不能标 complete。无法传入的内容明确列为未覆盖范围。

验收必须绑定实际成果版本：记录路径、生成时间及适合该成果的文件校验值或版本标识，并指明各预览和检查对应哪个版本。验收后文件变化则使相关检查失效，重新检查受影响项目；未通过的修改版不能沿用旧版“通过”。交付前核对交付文件与验收版本一致。

验收通过后交付实际成果、验证范围及剩余限制，保留对话和记录。skill 文件检查通过不等于真实账户工作流已跑通。
