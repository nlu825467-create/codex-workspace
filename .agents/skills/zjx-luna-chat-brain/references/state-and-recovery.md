# 任务记录与恢复

## 记录结构

工作目录创建 `.zjx-luna-chat-brain/<日期时间-短任务名>/`，不覆盖旧任务，只保留任务必要内容，不保存凭据或验证码。

- `state.json`：状态、实际模型/等级、对话 URL、标签、当前步骤、待发消息状态、最近完成动作、下一动作及阻碍。
- `user-request.md`：用户原始要求与依次追加的变更。
- `exchanges/001-user.md`、`001-chat.md`：实际发送文本和实际完整回复，按轮编号。
- `actions.md`：操作序号、对应回复、执行事实、证据路径。
- `evidence/`：必要截图、输出和资料摘录。
- `decisions.md`：存在分歧时记录争议观点、支持/反对证据、未知条件、预先约定的验证标准、验证结果、结论、方案版本和重新讨论的触发条件。保留未解决分歧，不只记录最终共识。
- `materials.md`：资料编号、路径或来源、版本标识、发送轮次、已发送范围、缺失范围和关键内容接收确认。
- `acceptance.md`：成果版本、路径、生成时间、校验值或其他适当标识、对应预览/检查、逐项验收、未覆盖范围及失效记录。
- `work-units.md`：每个工作单元的任务类型、Chat 决策/执行材料来源轮次、实际工具操作、结果证据及版本。写作必须有正文来源，设计可由规格关联生成工具输出，操作由指令关联完成状态；缺关键决策或未落实的单元标未完成。恢复旧任务时保留并读取已有 content-sources.md，不删除原记录。

状态采用 initializing、awaiting_chat、executing、awaiting_review、needs_user、complete。未知模型记 unknown，尚无 URL 记 null，配置核验使用明确布尔值。此处仅本地记录，不创建宿主 goal 或 automation。

## 保存时机

任务目录是权威记录位置，state.json 中记录 record_root；项目目录的使用说明可链接或注明复制自此处，不另建互相冲突的验收结论。旧任务存在多个记录时先核对来源、合并事实并保留原文件，不能删除或覆盖未解问题。

执行前 work-units.md 写入单元编号、类型、Chat 来源、材料位置/版本、前提与待执行动作；执行后写工具、结果与证据。交付前检查无空白工作单元、缺来源或缺证据。acceptance.md 记录每个要求的证据、Chat 判定、版本、剩余检查与 preview/candidate/final 等级。缺少记录即不允许宣告 final，但记录齐全本身不证明成果正确。

模型回退授权记录原始用户消息、适用任务/账户/会话范围、允许回退配置和失效条件；只在原授权范围使用，不把另一任务的一次同意扩大成永久偏好。未确认型号仍记录 unknown，不能因获准默认模型而记已验证最新。

配置核验后保存标签；发送前保存消息并标 prepared；确认送达标 sent；完整回复后保存原文。动作开始前记录计划引用，成功后记实际结果。可靠更新状态，可写临时文件再替换。

状态还记录当前方案版本、批次编号、对应回复标识、输入版本和前提。无法取得消息标识时使用保存原文、轮次、时间与文本特征核对；不能编造平台消息 ID。

每个动作记录唯一编号及 prepared、running、succeeded、failed、unknown 状态，并保存适用前提、结果证据、恢复检查方式。开始前先写 prepared，实际开始时写 running，有明确结果才写 succeeded/failed。中断后的 running 先转 unknown 并核查，不能直接重做。证据应与动作对应，不只记录“完成”。

恢复前核对输入版本；文件可用校验值，页面可用相关现场快照或内容标识。只有影响当前动作的变化才要求重新决策，不因无关显示变化重复整个任务。

资料维护已发送/未发送范围。Chat 未收到内容的文件路径不能作为它已检查的证据。大资料分批传输，必要时请 Chat 指明需要全文读取的原始部分。

## 中断恢复

1. 读原始要求、状态、最近交流及完成动作。
2. 回原对话，核对最后送达消息与最新完整回复。
3. prepared 遇到网络不确定先查对话，再决定发送，不能重复提交。
4. 已成功动作不因中断重做；无法确认副作用时先收集事实，再请 Chat 决定。
5. 以用户口吻发送进度、现场事实和待解决问题，请 Chat 给恢复步骤。
6. 必须迁移时先验证新配置，传入原需求、变更、最新方案、完成项、关键证据及待办，保存旧地址和迁移原因。

## 无进展与完成

同一原因失败两次就提交完整尝试和错误，请 Chat 改路线；连续两轮仍无可执行方案时停止重复讨论，优先取得明确的证据采集方案。确需用户资料、偏好、权限或外部条件才能继续时报告阻碍，保存 needs_user。登录、额度或配置问题同样保留断点，不宣告完成。

讨论连续两轮没有新增证据、可检验解释或可执行验证步骤时，停止重复立场，优先转向信息采集；需要用户资料、偏好或权限才能继续时才记录 needs_user。证据不足不能用讨论轮数代替判断。恢复时同时读取 decisions.md，保留既定验证标准及未解争议。

完成时保存逐项验收和 Chat 实际看到的证据范围，标 complete。向用户交付真实成果和验证范围，不把 skill 结构检查通过说成真实账户流程已验证。

标 complete 前核对：各工作单元均有对应 Chat 决策和必要执行材料，以及实际执行证据；实际成果版本及与任务匹配的验收证据已提供给 Chat；所有验收条件已解决并重新审查。仅有冻结方案、核心段落审查或有条件通过时不能标 complete。分块发送记录编号、覆盖范围和送达状态，汇总验收必须明确对应同一完整版本。

验收后修改成果应记录哪些检查失效，并重新提交受影响内容。交付时核对实际文件版本与 acceptance.md 中已验收版本一致。阶段汇总按编号保存在 exchanges 中，链接原始证据，不能覆盖或删除原始记录。
